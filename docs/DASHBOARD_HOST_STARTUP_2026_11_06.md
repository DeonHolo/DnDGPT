# Dashboard host startup and updates

Runtime 1.4.1 fixes dashboard initialization when ChatGPT exposes both the MCP Apps bridge and window.openai. The previous bootstrap treated window.openai.callTool as a reason to skip ui/initialize and ui/notifications/initialized. ChatGPT's live timeout detail explicitly reported that the app did not finish initialization within five seconds. A successful render_dashboard tool response meant the server returned its data; it did not establish that the iframe mounted.

The regression browser fixture reproduced that missing readiness message. It also reproduced a separate startup crash when persisted view_preferences contained a layout without panels/details arrays. Existing host tests exercised the two interfaces separately and missed the hybrid case.

The dashboard now begins MCP Apps negotiation for every embedded host, including hosts that also provide compatibility globals. On a successful modern handshake it sends the initialized notification before processing host styling or fetching saved data. Compatibility-only hosts can begin after a 300ms grace period instead of waiting for the 15-second standard request timeout. A delayed modern handshake can recover one rejected compatibility read. Late bridge injection remains supported. Restored preferences receive safe array defaults.

This follows [OpenAI's standards-first UI guidance](https://developers.openai.com/plugins/build/chatgpt-ui): shared initialization and tool operations use the MCP Apps bridge; compatibility APIs remain a fallback. The existing separation between render and data tools remains. No new model tool call, authorization scope or gameplay rule is required.

Regression coverage executes the actual startup JavaScript in Node with standard, hybrid, compatibility-only, delayed and standalone hosts, plus partial/malformed preferences. The browser fixture additionally uses real authenticated local MCP transport and a disposable campaign to test notification updates and refreshes while retaining the mounted document. It records before/after results in ignored test-results files. The compatibility shortcut was introduced in commit `237ba1bf` on October 24; before the fix, `app/index.html` lines 1295–1297 bypassed modern negotiation when compatibility globals existed.

## Verified release

Published **1.4.1**, implementation `75b47a12917ae156105be6f97e4c456eeaeaace9`. [Isolated release CI](https://github.com/DeonHolo/DnDGPT/actions/runs/42224099312) and [main CI](https://github.com/DeonHolo/DnDGPT/actions/runs/42224539008) each passed all **807 tests**, isolated hosted imports, rule synchronization and packaging. The focused Windows run passed 11 cases. The in-app browser passed eight connection checks and six mode-launch checks, including unchanged saves/time while choosing a mode.

At 13:22 UTC on November 6, public health and the actual connected MCP reported 1.4.1. The entire public application dashboard matched the tested source, SHA-256 `cdb872df4dbaedd9a46970ff93ff5463cb7f2d57a4f051a4abe38617036d92a5`. Anonymous campaign/MCP requests remained 401. Native rulebook/hardener hashes are unchanged.

Actual ChatGPT Chrome verification at 13:31–13:32 UTC: opened the installed plugin's Open plugin entry, observed the rendered dashboard's data-ui-version=1.4.1, switched the Game dropdown to Sovereign System, and received the live saved-game listing. Connection details reported Connected to saved state and Dashboard build 1.4.1. No campaign was selected, advanced or modified. The working app tab was left open for the player. No ZIP, reconnect, new OAuth permission or CSP change was used.

The previously failed inline message cards continued to time out on retry, including after a page reload; they must not be reported as repaired in place. A fresh plugin launch works. Replaying cached UI from those earlier calls is a probable explanation, but their old inner document was not inspectable and that cache mechanism is unverified. Recovery verified here is Plugins → DnDGPT → Open plugin. Fresh inline model invocation and native Android remain untested. Local disposable saves verify actual save notifications and mounted refreshes; no production gameplay write was needed.
